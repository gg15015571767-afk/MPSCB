### 一、 核心架构与 Agent 框架

#### Q1: 为什么选择 Nanobot 框架？相比于 LangChain / LlamaIndex 有什么优势？

- **考察意图**：考察技术选型的思考与对开源框架的理解。

  

- **答题要点**：

  - **专注与轻量**：Nanobot 原生提供了 Agent 极简基座、多平台 Channel 接入、消息总线、MCP 加载与 Provider 抽象，无需像 LangChain 一样引入过重且复杂的链式封装。

    

  - **聚焦业务逻辑**：框架帮你搞定了底层的长连接网关与消息路由，开发者能将 100% 精力放在客服业务闭环（FAQ/RAG/工单）的研发上。

    

#### Q2: 项目中的“三段式”问答流程具体是怎么流转的？

- **考察意图**：考察系统整体架构设计与请求链路处理逻辑。

  

- **答题要点**：

  1. **第一级 (FAQ 精确匹配)**：对于极高频的查话费、报修等固定问题，优先走字符串/规则精确匹配，毫秒级响应且零幻觉。

     

  2. **第二级 (向量 RAG + LLM 生成)**：未命中 FAQ 时，在 9.1 万条向量库中做相似度检索，结合 DeepSeek 生成润色后的回答。

     

  3. **第三级 (兜底转人工工单)**：若检索相似度低于 0.55 阈值，触发 MCP 工单 Server 自动创建工单，引导用户转人工。

     

#### Q3: 自定义 MCP (Model Context Protocol) Server 是怎么实现的？解决了什么问题？

- **考察意图**：考察对大模型前沿协议（MCP）的实践应用。

  

- **答题要点**：

  - **实现**：基于 MCP 规范定义了工单服务 Server（`mcp_server/`），暴露工单创建、状态查询等 Tool API。

    

  - **优势**：标准化了 Agent 与外部系统（工单数据库）的通信协议，解耦了业务代码，方便以后将工单能力无缝复用到其他 Agent 体系中。

    

### 二、 RAG 检索、数据与评估（重点深挖区）

#### Q4: 为什么选择 RAG 方案，而不是直接对 LLM 进行微调（Fine-Tuning）？

- **考察意图**：考察对大模型技术落地选型的理解。

  

- **答题要点**：

  - **知识实时性**：电信业务（套餐/政策）变更频繁，RAG 只需要更新数据库/FAQ 即可秒级生效，而微调成本高且时效慢。

    

  - **可追溯与可解释**：RAG 能清晰定位检索到的参考原文，方便溯源。

    

  - **抑制幻觉**：客服场景要求绝对准确，RAG 配合 Prompt 能极大降低模型自由发挥造成的幻觉。

    

#### Q5: Embedding 模型是怎么选型的？为什么是 `bge-small-zh-v1.5`？

- **考察意图**：考察对向量模型属性、维度与性能平衡的理解。

  

- **答题要点**：

  - **语言匹配**：中文语义检索必须用专门针对中文预训练的模型（一开始用英文模型效果差，换成 BAAI 中文向量模型后大幅提升）。

    

  - **维度与性能**：原生维度为 **384 维**，相比 768/1024 维的大模型，384 维在内存占用小、检索速度快（毫秒级）的同时，实测准确度依然达到了 0.864。

    

#### Q6: 检索质量评估中的平均相似度（0.864）是怎么计算出来的？

- **考察意图**：考察 RAG 评估指标（Evaluation Metrics）与 Ground-Truth 数据集的使用。

  

- **答题要点**：

  - **数据源**：自建包含 9.1 万条带 Ground-Truth“最佳回答”的真实数据集。

    

  - **评估逻辑**：运行 `eval_retrieval.py` 自动化脚本，用测试集提问去检索 Top-1 结果，计算检索出的回答向量与标准答案（Ground-Truth）向量之间的**余弦相似度（Cosine Similarity）**，最后对所有样本求算术平均。

    

#### Q7: 为什么把语义匹配阈值从 0.45 调优到了 0.55？怎么确定 0.55 是最优的？

- **考察意图**：考察超参数调优（Grid Search）与 Precision-Recall Trade-off 的分析能力。

  

- **答题要点**：

  - **Bad Case 分析**：0.45 时存在同类业务词误匹配（如“翼支付白条”误配到“欠费停机”，余弦分数为 0.48）。

    

  - **网格搜索**：以 0.05 为步长做遍历，发现 **0.55** 能消除 95% 以上的错配，同时保留了 98.7% 的高质量召回（相似度 >0.7），在“精准度”与“覆盖率”之间达到了最佳平衡。

    

### 三、 业务闭环与数据运营

#### Q8: 系统是如何实现知识库“动态更新闭环”的？（`suggest_faq` 的原理）

- **考察意图**：考察智能客服系统上线的持续运营与自我演进能力。

  

- **答题要点**：

  - **日志捕获**：当用户提问相似度低于 0.55 阈值或转人工时，系统存入未命中日志。

    

  - **高频挖掘**：运行 `suggest_faq.py` 脚本对未命中提问进行频次统计与语义聚类。

    

  - **运营审核**：自动整理并输出高频未命中问题建议，引导运维人员补充标准答案至 FAQ，实现知识库的持续演进。

    

#### Q9: 转人工工单与满意度评价是如何设计的？

- **考察意图**：考察完整客服业务链条的工程设计。

  

- **答题要点**：

  - **工单创建**：用户选择转人工或多次触发未命中时，系统通过 MCP 工具自动创建含有对话上下文的 SQLite 工单记录。

    

  - **评价闭环**：服务结束后推送 1–5 星满意度评价，评价数据入库并汇总到 `stats_cli.py` 运营报表中。

### 二、 Agent 架构与核心原理（八股与前沿）

#### Q3：什么是“智能路由设计”（Intent / Smart Routing）？你在系统中是如何实现的？

- **考察点：** 对复杂 Agent 系统的中枢调度理解。
- **回答切入点：**
  - 阐述意图分类 + 分发机制：根据用户 Query 的复杂度或领域，智能路由给不同模型（如轻量模型降本/复杂推理模型）或子 Agent（如售后/查询）。
  - 提到如何通过语义相似度（Vector Search）结合少量 Prompt 规则实现毫秒级快速分发。

#### Q4：讲讲 ReAct、Plan-and-Execute（规划执行）与 Reflexion（反思）的区别？

- **考察点：** Agent 推理与行动模式（Planning）。
- **回答切入点：**
  - **ReAct**（Think-Act-Observe 循环）：适合动态、路径不确定性高的探索任务，边想边干。
  - **Plan-and-Execute**：先生成 Task List 再分步执行，适合确定性高、步骤长的多步复杂任务，省 Token 且不易跑偏。
  - **Reflexion**：增加了自我评测与错误记忆机制，当工具返回 Error 时触发重试或策略修正。

#### Q5：什么是 MCP（Model Context Protocol）协议？它解决了什么问题？

- **考察点：** 对大模型前沿协议的敏感度。
- **回答切入点：**
  - 说明 MCP 解耦了“大模型应用”与“外部数据/工具服务”。过去每个 Agent 框架都要重新写一套 Tool 工具接口；MCP 实现了**一次编写，多端挂载**的标准化（包含 Resources、Tools、Prompts 三大原语）。

#### Q6：如何解决 Agent 在多轮 Tool Calling 中的“死循环”与“上下文爆炸”问题？

- **考察点：** 生产环境极其真实的工程坑点。
- **回答切入点：**
  - **死循环：** 设置最大执行步数（Max Iterations）；记录历史 Action 序列，发现连续 N 次重复 Tool + 参数时触发打断或人工介入（Human-in-the-loop）。
  - **上下文爆炸：** 对历史工具返回做摘要压缩（Summary）；使用滑动窗口保留关键记忆；把大型 JSON 输出过滤为只保留 Agent 所需字段。

### 三、 工程化、测试与部署

#### Q7：你们项目中的 CI 自动化测试和 Docker 容器化是怎么落地的？

- **考察点：** 自动化运维与环境一致性能力。
- **回答切入点：**
  - **CI 自动化：** 结合 GitHub Actions + PyTest，每次代码 Push 时对 Prompt 生成结果和工具调用做**回归测试（Regression Testing）**，防止修改代码导致 Agent “退化”。
  - **Docker：** 实现 Agent 运行环境、依赖项（Python 库、数据库连接等）的沙箱隔离，保障“开发-测试-部署”全流程环境一致。

#### Q8：如何保证 Tool Calling 的准确性与安全性？

- **考察点：** 护栏（Guardrails）与工程鲁棒性。
- **回答切入点：**
  - **准确性：** 优化 Tool Description 的 JSON Schema 定义；参数校验（Pydantic）；必要时对参数补全做 Few-shot 示例。
  - **安全性：** 对破坏性操作（如删除/付款）增加二次确认；给代码执行器加 Docker/沙箱隔离；严格限制 API 密钥权限白名单。

### 五、 场景设计与开放题（大厂二面/三面必考）

#### Q9：设计一个企业级的智能客服 Agent，要求支持商品查询、物流追踪、退款处理及人工接管，你会怎么架构？

- **考察点：** 系统架构设计能力。
- **回答策略（分层回答）：**
  1. **接入与路由层：** 接入 Webhook/RESTful API；通过**智能路由**分发请求（例如：聊天打招呼 -> 规则回复；退款/复杂诉求 -> 路由至退款 Agent）。
  2. **决策与工具层：** 采用 Plan-and-Execute 规划复杂退款流程（查订单 -> 查物流 -> 判断合规 -> 调 API 发起退款）。
  3. **记忆与状态层：** Redis 存储 Session 短期记忆，向量数据库存储用户画像长期记忆。
  4. **兜底与安全性：** 设置 Human-in-the-loop（高额退款转人工），引入超时降级与重试机制保障高可用。
